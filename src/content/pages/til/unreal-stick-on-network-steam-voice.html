게임 기능보다 먼저 검증할 네트워크 기준 만들기

Stick On은 두 플레이어가 자재로 길을 만들고 서로를 구조하면서 건물 외벽을 오르는 협동 게임입니다. 팀에서 네트워크를 맡으며 가장 먼저 정한 목표는 두 플레이어가 같은 대상을 조작해도 서버가 일관된 결과를 결정하게 만드는 것이었습니다.

작업 초기에는 다른 담당자의 캐릭터·인벤토리·건설 시스템이 준비되지 않았습니다. 실제 기능을 기다리는 대신, 연결과 초기화, 서버 권한을 따로 확인할 수 있는 L_NetworkTest 맵을 만들었습니다. 기능 통합 후 문제가 생겨도 기존 네트워크 경로와 새 기능을 나누어 살펴볼 기준점이 필요했습니다.

구조는 한 플레이어가 서버와 로컬 플레이어를 겸하는 2인 리슨 서버입니다. 임시 캐릭터는 큐브로 표시하고 기본 이동에는 CharacterMovementComponent를 사용했습니다.

클래스역할
NetworkTestGameMode입장 제한, 준비 확인, 행동의 서버 검증
NetworkTestGameState준비 상태와 테스트 시작 정보 복제
NetworkTestPlayerController로컬 상태 확인, 소유 RPC 요청, 진단
NetworkTestCharacter기본 이동이 가능한 임시 캐릭터
NetworkTestTarget서버 권한 검증용 큐브
NetworkTestHUD연결·준비·행동 결과 표시

처음에는 클래스 이름에 테스트 도구를 뜻하는 Harness를 사용했지만, 팀원이 역할을 쉽게 이해하도록 NetworkTest로 통일했습니다.

접속 완료와 게임 시작 준비를 구분하기

화면에 큐브 두 개가 나타나도 연결 검증이 끝난 것은 아니었습니다. HUD와 로그에서 양쪽의 참가자 목록이 같은지, 로컬 플레이어 ID가 서로 다른지, 각 플레이어에게 Pawn이 있고 로컬 Controller가 자신의 Pawn을 소유하는지 확인했습니다.

정원 제한은 서버의 PreLogin에서 먼저 검사하고, 실제 Controller를 생성하는 Login에서도 다시 검사했습니다. PreLogin 통과를 자리 예약으로 취급하지 않고 최종 입장 단계에서도 두 명 제한을 확인하기 위해서입니다.

다음 문제는 초기화 순서였습니다. 서버에 두 명이 접속한 시점과 클라이언트가 필요한 객체·복제 상태를 받은 시점은 같다고 볼 수 없었습니다. 그래서 접속 인원과 별도로 기술적 준비 확인을 추가했습니다.

두 플레이어 접속
                → 각 클라이언트가 PlayerState·Pawn·소유 관계 확인
                → 자신이 소유한 PlayerController로 준비 확인 RPC 전송
                → 서버가 현재 Pawn·RoundId·Generation 재검사
                → 두 명 모두 준비되면 Mock 시작, 캐릭터 조작 허용

RoundId는 판을 구분하고, Generation은 같은 테스트 월드 안에서 준비 조건이 바뀌었는지 구분합니다. 시작 전에 참가자가 나가거나 새로 들어오면 세대를 변경해 이전 준비 확인을 무효화했습니다. 같은 확인 요청이 반복되어도 시작 횟수는 한 번만 증가하도록 했습니다.

이번 준비 확인은 테스트용 Mock 시작입니다. 실제 캐릭터·인벤토리 초기화나 시작 본드 지급은 아직 연결하지 않았습니다. 자동 시작과 준비 버튼 중 어떤 UX를 사용할지도 별도 결정 사항입니다.

공유 대상의 상태는 서버가 결정하기

실제 자재가 없어도 서버 권한 경로는 확인할 수 있었습니다. 가까운 테스트 큐브를 한 번 활성화하는 행동을 만들고, 두 플레이어가 같은 큐브에 요청해도 활성화 횟수가 한 번인지 검사했습니다.

로컬 입력
                → 소유 PlayerController의 Server RPC
                → 서버 GameMode에서 요청 조건 검사
                → 테스트 큐브의 상태 변경
                → 복제된 상태를 양쪽 화면에 반영

공유 큐브의 Owner를 플레이어 사이에서 바꾸는 대신, 요청은 각 플레이어가 소유한 Controller를 통해 전달했습니다. 서버는 클라이언트가 보낸 값을 그대로 적용하지 않고 다음 조건을 확인했습니다.

  • 현재 등록된 참가자의 요청이며, 현재 라운드와 초기화 세대에 해당하는가?
  • 테스트 시작 준비가 완료되었는가?
  • 요청에 포함된 Pawn이 요청자의 실제 Pawn인가?
  • 대상이 유효하고 등록된 테스트 큐브이며, 서버 기준 거리 안에 있는가?
  • 이미 활성화된 대상은 아닌가?

활성화 결과는 대상 Actor의 복제 상태에 저장하고, 성공·실패 이유를 알리는 Client RPC는 진단용으로 사용했습니다. 지속적으로 유지할 상태와 일회성 응답을 구분한 것입니다.

이 테스트에서 중복 실행을 막는 기준은 대상의 ‘활성화 완료 상태’였습니다. 모든 아이템 소비에 적용할 수 있는 범용 중복 방지 시스템을 만든 것은 아닙니다. 본드·못 소비는 실제 기능을 통합할 때 각 처리 단위에 맞춰 설계해야 합니다.

성공뿐 아니라 거절 후 상태도 확인하기

PIE에서는 두 플레이어가 보이고 움직이는지 직접 확인했습니다. 처음에는 화면이 검게 보여 스폰 문제를 의심했지만, 조명을 추가하자 정상적으로 확인할 수 있었습니다. 화면에서 보이지 않는 현상과 네트워크 연결 실패를 구분할 필요가 있었습니다.

반복 검증에는 별도의 서버·클라이언트 프로세스를 실행하고 로그를 비교하는 PowerShell 스크립트를 사용했습니다. 아래는 Stick On 프로젝트에 만든 테스트 스크립트의 실행 명령입니다.

./Scripts/Network/Test-NetworkConnection.ps1
                ./Scripts/Network/Test-NetworkConnection.ps1 -Readiness
                ./Scripts/Network/Test-NetworkConnection.ps1 -Authority
시험확인한 내용
연결호스트 역할 교체, 동일 참가자 목록, 소유 관계, 정원 제한
준비준비 지연, 준비 전 퇴장, 중복 확인, 잘못된 세대 거절
권한정상·동시 요청, 거리 밖 대상, 다른 Pawn 주장, 제거된 대상

정상 요청이 성공하는지와 함께 거절된 요청이 상태를 바꾸지 않는지도 확인했습니다. 한 PC의 별도 프로세스로 연결·준비·권한 시나리오를 검증했지만, NullRHI 실행 결과가 화면 품질이나 실제 인터넷 환경까지 보장하지는 않습니다.

Steam을 추가한 뒤에도 기존 시험을 반복할 수 있도록 로컬 회귀 스크립트에는 -nosteam과 OnlineSubsystem NULL을 명시했습니다. Steam 서비스 상태와 독립적으로 서버 처리 규칙을 확인하기 위한 구성입니다.

Steam 세션으로 방 생성·검색·참가 연결하기

다음 단계는 팀원과 접속할 세션 메뉴였습니다. Advanced Sessions와 Advanced Steam Sessions 플러그인을 설치하고, 게임 통신에는 SteamSockets를 사용하도록 설정했습니다.

세션 로직은 UNetworkTestSessionSubsystem이라는 GameInstanceSubsystem에 두었습니다. 기존 BP_NetworkTestGameInstance를 유지하면서 기능을 추가하기 위한 선택이었습니다.

메뉴는 WBP_NetworkTestMenu로 표시합니다. 버튼과 레이아웃은 부모 C++ 클래스의 WidgetTree에서 생성하고, 세션 처리는 C++에서 Online Subsystem 인터페이스를 호출하도록 구현했습니다.

호스트: 방 만들기 → Steam 세션 생성·시작 → 테스트 맵을 listen으로 열기
                참가자: 방 검색 → 결과 선택 → 세션 참가 → 호스트 주소로 ClientTravel

참가자는 자신의 테스트 맵을 별도로 여는 것이 아니라, 참가한 세션에서 얻은 접속 주소로 이동하도록 연결했습니다. 개발용 App ID 480을 사용하므로 검색에서 테스트 방을 구분할 프로젝트 식별 속성도 추가했습니다.

STICK_ON_TEST = StickOn_NetworkTest_v1

이 값은 방을 구분하는 검색 필터이며 사용자 인증을 대신하지 않습니다. 생성·검색·참가 중에는 버튼을 비활성화하고, 실패 메시지와 기존 세션 정리 기능을 연결했습니다. 게임으로 이동할 때는 UI 전용 입력 모드를 게임 입력으로 복원했습니다.

현재 확인한 범위는 빌드, 메뉴 로드·렌더링, 기존 로컬 연결 회귀입니다. Steam을 통한 두 PC 접속 성공 여부는 실환경 검증이 남아 있습니다.

기존 세션 구성을 활용한 Steam VoIP

음성 채팅은 처음에 EOS Voice Chat을 검토했습니다. 검토한 통합 방식에는 EOS 로그인·로비 또는 별도 토큰 발급 백엔드가 필요했습니다. 이번 프로젝트에서는 별도 백엔드를 두지 않기로 했고, 이미 사용 중인 Advanced Sessions의 음성 기능을 고려해 Steam VoIP를 선택했습니다.

우선 구현한 것은 Push-to-Talk입니다. V 키를 누르면 송신 시작을 요청하고, 키를 놓으면 송신을 중단하도록 연결했습니다. 방을 나가거나 Controller가 종료될 때도 송신을 중단합니다.

프로젝트에 추가한 설정

; DefaultEngine.ini
                [OnlineSubsystem]
                DefaultPlatformService=Steam
                bHasVoiceEnabled=true
                
                [Voice]
                bEnabled=true
; DefaultGame.ini
                [/Script/Engine.GameSession]
                bRequiresPushToTalk=true

C++ 입력 처리에는 PlayerController의 StartTalking()과 StopTalking()을 사용했습니다. 음성 데이터를 게임 RPC로 직접 보내는 코드를 만들지 않고 OSS 음성 경로를 사용했으며, 로컬·원격 Talker 등록은 엔진의 Steam 세션 등록 경로에 맡겼습니다.

현재는 설정과 입력을 연결하고 Editor 빌드를 통과한 단계입니다. 실제 양방향 마이크 송수신, 키 해제 시 송신 중단, 재참가 후 동작은 새 패키지로 두 PC에서 확인해야 합니다. 상대 음소거와 발화 표시 UI도 후속 작업입니다.

배운 점과 다음 통합 기준

이번 작업에서 배운 핵심은 ‘접속했다’, ‘게임을 시작할 준비가 됐다’, ‘행동을 실행해도 된다’를 각각 검증해야 한다는 점입니다. 접속 여부만으로 초기화 완료를 판단하거나, 클라이언트의 요청만으로 공유 상태를 바꾸면 안 된다는 기준을 테스트 환경에서 구체화했습니다.

항목기록 시점의 상태
2인 연결·소유 관계·정원 제한구현 및 로컬 프로세스 검증
기술적 준비·단일 Mock 시작구현 및 로컬 프로세스 검증
큐브 서버 권한·상태 복제구현 및 로컬 프로세스 검증
Steam 세션 메뉴구현, 빌드·메뉴 표시 검증 / 두 PC 접속 미검증
Steam VoIP Push-to-Talk설정·입력 연결, 빌드 검증 / 양방향 송수신 미검증
실제 게임 기능 통합캐릭터·인벤토리·건설·승패 연결 예정

빌드 통과, 로컬 프로세스 시험 통과, 실제 두 PC 동작 확인은 서로 다른 검증 단계였습니다. 구현한 기능과 확인한 범위를 따로 기록해야 다음 작업에서 무엇을 믿고 어디부터 시험할지 명확해집니다.

다음에는 실제 캐릭터의 기본 이동을 먼저 통합하고 달리기·스태미나·턱 잡기·등반 순서로 연결할 계획입니다. 기능마다 서버가 결정할 상태, 클라이언트가 요청할 행동, 다른 플레이어에게 전달할 정보를 담당자와 정하고, 기존 연결·준비·권한 시험을 반복하겠습니다.
