Unreal 인터페이스와 델리게이트: 요청과 알림 분리하기

TIL · 게임 엔진 · 2026.09.22

좋은 구조는 클래스와 함수를 많이 만드는 구조가 아니라, 현재 필요한 의미와 경계를 정확히 드러내는 구조입니다. 의미 없는 중간 계층을 걷어내는 리팩터링 기준을 세운 뒤, 서로 다른 객체에 같은 기능을 요청하는 인터페이스와 상태 변화를 여러 객체에 알리는 델리게이트를 데미지 처리 흐름으로 연결해 정리합니다.

리팩터링은 의미를 선명하게 만드는 일

긴 함수에서 서로 다른 작업이 섞여 있거나, 복잡한 조건이 무엇을 뜻하는지 읽기 어렵다면 함수 추출이 도움이 됩니다. 핵심은 줄 수를 줄이는 일이 아니라 구현의 의도를 이름으로 드러내는 것입니다. 

if (CurrentHealth <= 0.0f)
{
    return;
}

조건 자체는 짧지만 여러 호출부에서 반복된다면 의미 있는 질의를 추출할 수 있습니다.

bool UHealthComponent::IsDead() const
{
    return CurrentHealth <= 0.0f;
}

if (IsDead())
{
    return;
}

IsDead()는 계산을 크게 줄이지 않지만 “왜 여기서 중단하는가”를 설명합니다. 반대로 이름이 본문보다 더 많은 정보를 주지 못하고 호출을 따라가는 비용만 만든다면 함수 인라인을 검토합니다. 함수 개수나 길이가 아니라 호출부에서 얻는 의미를 기준으로 판단해야 합니다.

  • 한 함수에 서로 다른 작업이 섞였다면 책임별로 추출합니다.
  • 복잡한 조건이나 반복문에 이름을 붙이면 의도가 선명해지는지 봅니다.
  • 추출한 함수가 단순 위임만 하고 새로운 의미를 제공하지 않는다면 인라인을 검토합니다.
  • 리팩터링과 기능 변경을 한 번에 섞지 않아 동작 보존 여부를 확인하기 쉽게 만듭니다.

게으른 요소를 판단하는 기준

함수, 클래스, 인터페이스는 이름과 책임, 변경 경계를 표현하지만 유지 비용도 만듭니다. 짧다는 이유만으로 게으른 요소는 아닙니다. 앞의 IsDead()처럼 중요한 도메인 의미를 제공한다면 남길 이유가 있습니다.

반면 상태도 규칙도 없는 DamageHelper가 다른 클래스의 CalculateDamage()만 그대로 호출한다면 별도 계층이 제공하는 가치가 있는지 확인해야 합니다. 호출 경로만 늘어난다면 제거하거나 실제 책임이 있는 객체로 합치는 편이 낫습니다.

게으른 요소의 기준은 크기가 아니라 “이 요소가 독립적인 의미, 책임 또는 변경 경계를 제공하는가?”입니다.

Unreal 프로젝트에서는 C++ 검색 결과만 보고 바로 제거해서는 안 됩니다. 클래스와 함수가 Blueprint에서 구현·호출되거나, 에디터 프로퍼티와 데이터 에셋에서 참조될 수 있기 때문입니다. Find References, Blueprint 검색, 에셋 참조와 리플렉션 노출 여부까지 확인한 뒤 정리합니다.

추측성 일반화를 피하기

아직 확인되지 않은 미래 요구를 위해 사용하지 않는 인터페이스, 전략 클래스, 설정 옵션을 미리 만드는 일을 추측성 일반화라고 합니다. 사용하지 않는 코드도 이름을 이해하고 테스트하고 변경에 맞춰 유지해야 하므로 비용이 생깁니다.

확장 가능성을 모두 없애자는 뜻은 아닙니다. 지금 존재하는 두 구현의 공통 계약이 필요하거나, 이미 변경 빈도가 높은 경계를 격리해야 한다면 추상화의 근거가 있습니다. “나중에 필요할지도 모른다”가 유일한 이유라면 현재 요구를 가장 단순하게 구현하고 실제 변화가 생겼을 때 공통점을 추출하는 편이 안전합니다.

Unreal 인터페이스의 역할

인터페이스는 객체가 제공하는 기능의 약속입니다. Enemy, Player, 보물 상자처럼 상속 계층과 내부 상태가 서로 다른 객체에도 “데미지를 받을 수 있다”는 같은 요청을 보낼 수 있게 합니다. 호출자는 구체 타입과 처리 방법을 알 필요가 없습니다.

  • Enemy와 Player는 체력을 감소시키고 사망 여부를 판정할 수 있습니다.
  • 부술 수 있는 상자와 벽은 별도의 체력 없이 한 번의 요청으로 파괴될 수 있습니다.
  • 바닥과 파괴 불가능한 벽은 인터페이스를 구현하지 않아 요청 대상에서 제외됩니다.

UInterface 계열은 Unreal 리플렉션 시스템에 인터페이스 타입을 알리는 껍데기이고, I 접두사의 네이티브 클래스가 실제 함수 계약을 선언합니다. 구현할 클래스는 I 클래스를 함께 상속합니다.

인터페이스 선언과 호출

// Damageable.h
#pragma once

#include "CoreMinimal.h"
#include "UObject/Interface.h"
#include "Damageable.generated.h"

UINTERFACE(MinimalAPI, BlueprintType, Blueprintable)
class UDamageable : public UInterface
{
    GENERATED_BODY()
};

class MYGAME_API IDamageable
{
    GENERATED_BODY()

public:
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable, Category = "Damage")
    void ReceiveHit(float Damage);
};

C++ 구현 클래스는 _Implementation 접미사가 붙은 함수를 재정의합니다.

class AEnemy : public ACharacter, public IDamageable
{
    GENERATED_BODY()

public:
    virtual void ReceiveHit_Implementation(float Damage) override;
};

void AEnemy::ReceiveHit_Implementation(float Damage)
{
    Health = FMath::Max(0.0f, Health - Damage);
}

호출할 때는 클래스의 타입 정보로 구현 여부를 확인하고 생성된 Execute_ 함수를 사용합니다. 이 경로는 C++ 구현뿐 아니라 Blueprint에서만 구현한 경우도 처리합니다. 

void ApplyWeaponDamage(AActor* HitActor, float Damage)
{
    if (!IsValid(HitActor))
    {
        return;
    }

    if (HitActor->GetClass()->ImplementsInterface(UDamageable::StaticClass()))
    {
        IDamageable::Execute_ReceiveHit(HitActor, Damage);
    }
}

Cast<IDamageable>()만으로 판별하면 Blueprint에서만 추가한 인터페이스 구현은 찾지 못할 수 있습니다. Blueprint 구현 가능성이 있다면 ImplementsInterface와 Execute_ 호출을 사용합니다.

델리게이트의 역할

인터페이스가 대상에게 “이 기능을 수행하라”고 요청하는 계약이라면, 델리게이트는 “이 사건이 발생했다”고 구독자에게 알리는 호출 연결입니다. 발신자는 누가 반응하는지 몰라도 되고, 구독자는 발신자의 내부 처리에 끼어들지 않고 상태 변화에 반응할 수 있습니다.

예를 들어 HealthComponent가 데미지를 계산한 뒤 체력 변경 이벤트를 발행하면 체력 바, 피격 효과, 사운드가 각각 구독할 수 있습니다. HealthComponent가 이 세 시스템을 직접 참조하지 않으므로 새 반응을 추가해도 핵심 데미지 로직은 바뀌지 않습니다. 

DECLARE_DYNAMIC_MULTICAST_DELEGATE_TwoParams(
    FOnHealthChanged,
    float, CurrentHealth,
    float, MaxHealth);

UCLASS(ClassGroup = (Combat), meta = (BlueprintSpawnableComponent))
class UHealthComponent : public UActorComponent
{
    GENERATED_BODY()

public:
    UPROPERTY(BlueprintAssignable, Category = "Health")
    FOnHealthChanged OnHealthChanged;

    void ApplyDamage(float Damage);
};

void UHealthComponent::ApplyDamage(float Damage)
{
    CurrentHealth = FMath::Clamp(CurrentHealth - Damage, 0.0f, MaxHealth);
    OnHealthChanged.Broadcast(CurrentHealth, MaxHealth);
}

델리게이트 종류와 선택 기준

종류호출 대상Blueprint 노출적합한 상황
Single-cast하나Dynamic 변형에서 가능완료 콜백, 하나의 전략 함수
Multicast여러 개Dynamic 변형에서 가능상태 변경과 게임플레이 사건 알림
Native선언에 따라 하나 또는 여러 개아니요C++ 안에서만 쓰는 연결
Dynamic선언에 따라 하나 또는 여러 개예리플렉션, 직렬화, Blueprint 바인딩이 필요한 연결

하나의 결과를 돌려받아야 하는 호출은 single-cast가 자연스럽습니다. 여러 시스템이 독립적으로 반응해야 하는 사건은 multicast가 적합합니다. 멀티캐스트 델리게이트는 바인딩된 함수의 호출 순서를 보장하지 않고 반환값도 지원하지 않으므로, 구독자 사이의 실행 순서나 결과 조합이 필요하다면 명시적인 조정 객체를 두는 편이 낫습니다.

C++에서만 사용할 때는 native 델리게이트로 충분합니다. Blueprint에서 이벤트를 연결해야 한다면 dynamic 델리게이트를 선택합니다. 편의 때문에 모든 이벤트를 dynamic multicast로 만들기보다 실제 소비자가 누구인지 먼저 확인합니다.

바인딩 수명 관리

델리게이트는 발행 시점뿐 아니라 연결이 살아 있는 기간까지 설계해야 합니다. 구독자는 초기화 시점에 바인딩하고, 더 이상 이벤트를 받아서는 안 되는 종료 시점에 해제합니다. 같은 객체를 여러 번 바인딩하면 한 사건에 반응이 중복될 수 있습니다. 

void UHealthBarWidget::BindHealth(UHealthComponent* Health)
{
    if (!IsValid(Health))
    {
        return;
    }

    BoundHealth = Health;
    Health->OnHealthChanged.AddDynamic(
        this, &UHealthBarWidget::HandleHealthChanged);
}

void UHealthBarWidget::NativeDestruct()
{
    if (UHealthComponent* Health = BoundHealth.Get())
    {
        Health->OnHealthChanged.RemoveDynamic(
            this, &UHealthBarWidget::HandleHealthChanged);
    }

    Super::NativeDestruct();
}

AddDynamic으로 연결할 함수에는 UFUNCTION()이 필요합니다. native delegate에서는 대상의 소유 방식에 맞춰 BindUObject, BindSP, BindRaw 등을 구분합니다. 특히 BindRaw는 대상 수명을 추적하지 않으므로 파괴된 객체를 호출하지 않도록 해제 책임을 명확히 해야 합니다.

상속·컴포넌트·인터페이스·델리게이트 비교

도구핵심 질문데미지 예
상속공통 기반과 기본 동작이 필요한가?모든 캐릭터의 이동과 생명 주기
컴포넌트상태와 구현을 여러 Actor에 재사용하는가?체력 값과 감소 규칙을 가진 HealthComponent
인터페이스서로 다른 객체에 같은 기능을 요청하는가?Enemy와 상자에 ReceiveHit 요청
델리게이트사건을 알리고 여러 반응을 분리하는가?체력 변경을 UI와 효과에 알림

이 도구들은 서로 배타적이지 않습니다. Actor가 IDamageable을 구현하고 실제 체력 상태는 HealthComponent에 위임하며, HealthComponent가 OnHealthChanged를 발행하는 구조처럼 함께 사용할 수 있습니다. 중요한 것은 추상화를 먼저 고르는 일이 아니라 요청, 상태, 알림의 책임을 먼저 구분하는 것입니다.

데미지 처리 흐름으로 연결하기

Weapon
  → HitActor가 IDamageable을 구현했는지 확인
  → Execute_ReceiveHit(HitActor, Damage)

Enemy / Player
  → 인터페이스 구현에서 HealthComponent.ApplyDamage 호출
  → HealthComponent가 체력과 사망 규칙 처리
  → OnHealthChanged.Broadcast(...)

HealthBar / HitEffect / Sound
  → 델리게이트를 구독해 각자의 반응 수행

Weapon은 대상의 구체 타입과 체력 보유 여부를 모릅니다. 파괴 가능한 상자는 인터페이스 요청에 즉시 파괴되고, Enemy는 HealthComponent로 규칙을 위임합니다. 체력이 바뀐 뒤 어떤 UI와 효과가 반응하는지도 Enemy가 알 필요가 없습니다. 이렇게 요청은 인터페이스, 재사용 상태와 규칙은 컴포넌트, 결과 전파는 델리게이트로 나누면 변경 이유가 섞이지 않습니다.

다만 프로젝트에 구현체가 하나뿐이고 교체 가능성도 없다면 인터페이스부터 만드는 것은 추측성 일반화가 될 수 있습니다. 반대로 호출 대상이 명확한데도 모든 것을 이벤트로 흩뿌리면 실행 흐름을 추적하기 어려워집니다. 현재 필요한 결합 방식 중 가장 단순한 것을 선택하고, 실제 중복과 변화가 확인될 때 경계를 확장해야 합니다.

배운 점

리팩터링의 목적은 구조의 수를 늘리는 것이 아니라 코드가 말하는 의미를 선명하게 만드는 것입니다. 짧은 함수라도 도메인 의도를 표현하면 유지하고, 책임 없는 중간 계층과 사용되지 않는 확장 지점은 줄입니다. Unreal에서는 C++뿐 아니라 Blueprint와 에셋 참조까지 확인해야 안전하게 제거할 수 있습니다.

인터페이스는 서로 다른 대상에 같은 요청을 보내는 계약이고, 델리게이트는 발생한 사건과 그 반응을 분리하는 연결입니다. 여기에 상태와 구현을 재사용하는 컴포넌트를 조합하면 호출자는 구체 타입을 몰라도 되고, 핵심 로직은 UI나 효과의 존재를 몰라도 됩니다. 앞으로는 “기능 요청인가, 상태 소유인가, 사건 알림인가?”를 먼저 묻고 도구를 선택하려고 합니다.
