Unreal 인벤토리 UI의 데이터와 화면 상태를 MVC로 분리하기

TIL · 게임 엔진 · 2026.09.17

인벤토리 위젯이 보유 아이템 조회, 분류 선택, 이벤트 구독, 슬롯 생성까지 맡으면서 변경할 위치가 불분명해졌습니다. 실제 보유 데이터는 Subsystem에 두고, Model이 표시 상태를 구성하도록 나누자 위젯은 입력 전달과 화면 표시만 담당할 수 있었습니다.

위젯에 모인 책임

기존 PriestMainMenuWidget은 분류 버튼을 누르면 값을 검증하고, PriestInventorySubsystem에서 목록을 조회한 뒤 슬롯을 다시 만들었습니다. 인벤토리 변경 이벤트의 구독과 해제도 위젯이 처리했습니다. 드래그를 시작하는 슬롯 위젯마저 Subsystem에 현재 수량을 물어보면서 화면 코드가 데이터 규칙을 함께 알게 됐습니다. 

분류 버튼 클릭
→ MainMenuWidget에서 분류 검증
→ 선택 분류 변경
→ Subsystem에서 목록 조회
→ 슬롯 생성과 화면 갱신

기능을 처음 만들 때는 이 경로가 짧고 이해하기 쉬웠습니다. 하지만 분류가 늘고 퀵슬롯 드래그가 추가되자 화면 배치만 바꾸려 해도 데이터 조회와 검증 코드를 함께 읽어야 했습니다. 인벤토리 수량이 바뀌었을 때 어느 위젯을 직접 갱신해야 하는지도 호출자마다 의식해야 했습니다.

이번 작업의 기준은 “어떤 클래스가 실제 아이템을 소유하고, 어떤 클래스가 현재 화면의 선택 상태를 소유하는가?”였습니다.

원본 데이터와 표시 상태 분리

역할클래스담당하는 일
원본 데이터PriestInventorySubsystem보유 아이템, 수량, 퀵슬롯 등록 정보
ModelPriestInventoryModel선택 분류와 표시 목록
ControllerPriestInventoryController사용자 요청 연결과 View 갱신
ViewPriestMainMenuWidget입력 전달, 격자와 텍스트 표시
슬롯 ViewPriestInventorySlotWidget개별 아이템 표시와 드래그 시작

예를 들어 “회복 포션 5개를 보유한다”는 Subsystem의 사실이고, “소모품 분류를 선택해 회복 포션을 보여준다”는 Model의 화면 상태입니다. 화면을 닫아 Model이 없어져도 보유 수량은 유지되어야 합니다. 그래서 아이템 추가와 차감은 계속 Subsystem의 API에서 처리하고, Model은 그 결과를 읽어 현재 화면에 필요한 상태로 바꿉니다. 기존 메뉴와 퀵슬롯의 MVC 흐름을 기준으로 인벤토리에도 같은 경계를 적용했습니다.

화면에 전달할 데이터 따로 만들기

이전에는 슬롯 위젯에 보유 아이템 구조체 FPriestOwnedItem을 그대로 전달했습니다. 여기에는 아이템 ID, 표시 이름, 수량처럼 실제 인벤토리와 가까운 값이 담겨 있었습니다. 그런데 슬롯이 드래그 가능 여부를 결정하려면 아이템 분류와 퀵슬롯 호환 여부도 알아야 했습니다. 그때마다 슬롯이 Subsystem에 다시 질문하면 View의 데이터 의존성이 남습니다.

이를 해결하기 위해 Model이 슬롯 하나에 필요한 값을 FPriestInventorySlotData로 구성하도록 했습니다. 아래는 글에서 사용하는 핵심 필드입니다. 

USTRUCT(BlueprintType)
struct FPriestInventorySlotData
{
    GENERATED_BODY()

    UPROPERTY(BlueprintReadOnly)
    FName ItemId = NAME_None;

    UPROPERTY(BlueprintReadOnly)
    FText DisplayName;

    UPROPERTY(BlueprintReadOnly)
    int32 Quantity = 0;

    UPROPERTY(BlueprintReadOnly)
    EItemCategory Category = EItemCategory::None;

    UPROPERTY(BlueprintReadOnly)
    bool bQuickSlotCompatible = false;
};

전체 화면에는 선택 분류와 슬롯 배열이 함께 필요하므로 FPriestInventoryViewData로 묶었습니다. View는 이 구조체를 받아 슬롯을 그릴 뿐, 아이템을 어디서 조회했는지는 알 필요가 없습니다. 다만 표시 데이터는 원본의 복사본입니다. View의 수량을 바꾼다고 실제 인벤토리 수량이 바뀌지는 않으며, 실제 변경은 반드시 Subsystem을 통해 이뤄져야 합니다.

분류 선택을 요청과 처리로 나누기

버튼 클릭을 받은 View는 분류를 직접 변경하지 않습니다. 선택하려는 분류를 요청 객체에 담고 InventoryRequest 이벤트를 보냅니다. View가 아는 것은 “사용자가 이 분류를 눌렀다”는 사실까지입니다. 

Request->Action = EPriestInventoryAction::SelectCategory;
Request->Category = InCategory;

InvokeViewEvent(
    EViewEventType::InventoryRequest,
    Request.Get()
);

Controller는 이벤트 종류와 요청 객체를 확인하고 Model->SetCategory()를 호출합니다. 분류가 유효한지와 선택 상태를 바꿀지는 Model이 결정합니다. Controller가 아이템 목록을 다시 조회하거나 슬롯을 생성하지는 않습니다. 

Request->bAccepted = Model->SetCategory(Request->Category);

SetCategory()는 무기, 탄약, 소모품, 재료처럼 허용한 분류만 받아들입니다. 잘못된 값이 들어오면 false를 돌려주고 기존 선택 상태를 유지합니다. 이미 선택한 분류라면 요청한 상태가 충족됐으므로 true를 반환하지만, 같은 목록을 다시 만드는 Refresh()는 호출하지 않습니다. 성공 여부와 실제 상태 변경 여부를 구분한 셈입니다.

데이터 변경을 화면에 전달하기

Model은 Subsystem의 OnInventoryChanged를 구독합니다. 보유 수량이 바뀌면 Model의 Refresh()가 선택한 분류의 최신 아이템을 가져와 표시 데이터로 변환하고, Model 변경 이벤트를 발생시킵니다. Controller는 새 데이터를 View에 전달합니다. 

Inventory->OnInventoryChanged.AddUniqueDynamic(
    this,
    &UPriestInventoryModel::Refresh
);

// Model의 Refresh() 안에서 표시 데이터를 다시 구성한 뒤
InvokePropertyChanged(0);

// Controller의 Model 변경 처리에서
View->SetInventoryData(Model->GetData());

최종 갱신 경로를 펼치면 다음과 같습니다.

Subsystem의 보유 데이터 변경
→ OnInventoryChanged
→ InventoryModel::Refresh()
→ 표시 데이터 구성과 변경 알림
→ InventoryController::HandleModelChanged()
→ MainMenuWidget::SetInventoryData()
→ 격자와 슬롯 갱신

이제 다른 게임플레이 코드가 Inventory->AddItem(...)을 호출하더라도 메뉴 위젯을 직접 찾아 갱신할 필요가 없습니다. Subsystem의 변경 이벤트가 같은 경로로 화면까지 전달됩니다. 분류 변경도 Model의 Refresh()를 사용하므로, 버튼 입력과 보유 데이터 변경이 마지막에는 동일한 표시 데이터 구성 로직으로 모입니다.

드래그 시작과 드롭의 검증 시점

기존 슬롯 위젯은 드래그를 시작할 때마다 Subsystem에서 현재 수량과 포션 정보를 확인했습니다. 변경 후에는 Model이 전달한 FPriestInventorySlotData로 빈 슬롯인지, 퀵슬롯에 넣을 수 있는지 판단합니다. 위젯은 드래그 표시를 만들고 아이템 ID를 드래그 작업에 담는 데 집중합니다. 

const bool bIsEmptySlot =
    Item.ItemId.IsNone() || Item.Quantity <= 0;

if (bIsEmptySlot || !Item.bQuickSlotCompatible)
{
    return;
}

여기서 표시 데이터는 드래그 시작 시점의 스냅샷이라는 점이 중요합니다. 사용자가 끌고 있는 사이 포션을 소비했다면 드래그 시작 때의 수량은 더 이상 최신 정보가 아닙니다. 따라서 드롭으로 실제 퀵슬롯을 등록할 때는 Model과 Subsystem의 최신 상태로 다시 검증해야 합니다. 화면에서의 상호작용 가능 여부와 실제 데이터 변경의 허용 여부를 같은 검사로 취급하지 않았습니다.

동기 이벤트에서 처리 결과 돌려받기

퀵슬롯 View는 이벤트로 등록을 요청하지만 InvokeViewEvent()의 반환형은 void입니다. 반면 Unreal의 NativeOnDrop()은 드롭 처리 성공 여부를 bool로 반환해야 합니다. 그래서 요청 객체에 기본값이 false인 bAccepted를 두었습니다. 

InvokeViewEvent(
    EViewEventType::QuickSlotRequest,
    Parameter.Get()
);

return Parameter->bAccepted;

이벤트를 받은 Controller가 Model->AssignItem(Parameter->ItemId)의 결과를 bAccepted에 기록합니다. 현재 이벤트 전달이 동기 방식이기 때문에 View는 호출이 끝난 직후 값을 읽을 수 있습니다. 처리할 Controller가 없다면 기본값 false가 남아 드롭을 성공으로 오인하지 않습니다. 향후 이벤트 전달 방식을 비동기로 바꾼다면 이 반환 방식도 함께 다시 설계해야 합니다.

이벤트 구독 해제와 객체 수명

클래스를 나누면 연결도 늘어납니다. 이 구조에는 Subsystem에서 Model로 가는 변경 이벤트와, Model·View에서 Controller로 가는 이벤트가 있습니다. 종료할 때는 연결을 만든 주체가 순서를 정해 해제해야 합니다. 

Controller.Disconnect()
→ View와 Model 이벤트 구독 해제

Model.Disconnect()
→ Subsystem 이벤트 구독 해제

Widget 제거

위젯을 먼저 제거한 뒤 남은 구독에 정리를 맡기지 않고, 정상 종료 경로에서 연결을 먼저 끊도록 했습니다. Model을 다른 Subsystem으로 다시 초기화할 때도 이전 구독을 해제한 뒤 새 대상을 연결합니다. BeginDestroy()의 해제 코드는 마지막 방어선으로 두되, 일상적인 종료를 GC 시점에 의존하지 않습니다.

메인메뉴 인벤토리 MVC는 PriestMainMenuPlayerController가 생성하고 연결합니다. 퀵슬롯 MVC는 PriestUIManager가 바인딩 배열로 유지합니다. View는 TWeakObjectPtr로 확인하고, 사용 중 유지할 Model과 Controller는 TObjectPtr로 보관합니다. 바깥 배열까지 UPROPERTY(Transient)로 선언해 구조체 안의 UObject 참조가 GC에 추적되도록 했습니다. Transient는 이 실행 중 연결 정보를 저장 대상에서 제외한다는 뜻입니다.

리뷰에서 점검한 설계

리뷰에서는 연결되지 않은 View의 이벤트를 조용히 무시하는 검사에 대해 질문을 받았습니다. 공통 SetView()가 이전 구독을 해제하고 현재 View만 구독하며, 이벤트 발신자가 자기 자신을 전달한다면 정상 경로에서 다른 View가 들어올 이유가 없습니다. 이런 상황을 단순히 반환해 버리면 잘못된 직접 호출이나 연결 오류를 숨길 수 있습니다.

반대로 하나의 메인메뉴 View를 여러 Controller가 구독하므로, 다른 기능의 이벤트를 받은 Controller가 이벤트 종류를 확인하고 반환하는 것은 정상적인 분기입니다. EventType != EViewEventType::InventoryRequest와 같은 검사는 유지할 이유가 있습니다. 방어 코드를 넣을 때는 “정상적으로 거절할 입력인가, 프로그램의 연결 규칙이 깨진 것인가”를 먼저 구분해야 한다고 배웠습니다.

함께 진행한 정리로, 인벤토리 Subsystem 안에 문자열로 박아 두었던 데이터 테이블 경로도 UDeveloperSettings의 소프트 참조로 옮겼습니다. 어떤 에셋을 사용할지는 프로젝트 설정에서 고르고, Subsystem은 그 설정을 읽어 로드합니다. MVC 자체의 변경은 아니지만 데이터 사용 코드와 에셋 선택을 분리한 사례였습니다. 기존의 로드 실패 및 Row Structure 검사는 유지했습니다.

검증과 남은 과제

작업 원문에는 C++ 빌드와 자동 테스트로 유효한 분류 선택, 잘못된 분류 거부와 기존 상태 유지, 인벤토리 변경에 따른 Model 갱신, 연결 해제 후 갱신 중단, 재연결 시 최신 데이터 반영, 퀵슬롯 등록·해제와 수량 갱신을 확인한 기록이 있습니다. 이 결과는 주로 Model과 Subsystem의 연동에 대한 검증입니다.

Controller의 모든 이벤트 경로나 WBP의 실제 동작까지 자동으로 확인한 것은 아닙니다. 특히 표시 구조체가 바뀌면 Blueprint 함수 핀에 영향을 줄 수 있으므로 WBP 컴파일과 실제 드래그·드롭 동작을 별도로 확인해야 합니다. 현재 목록 갱신은 슬롯을 모두 제거하고 다시 생성합니다. 아이템이 많아진다면 슬롯 재사용이나 변경된 항목만 갱신하는 방식이 필요할 수 있습니다. UIManager의 전투 피드백과 데미지 숫자 관리도 분리 후보로 남겨 두었습니다.

배운 점

MVC를 적용할 때 핵심은 클래스 이름을 세 종류로 만드는 일이 아니라 데이터의 원본, 화면 상태, 입력 처리, 갱신 경로를 각각 정하는 것이었습니다. 이번 분리로 인벤토리 규칙은 Subsystem과 Model에서, 화면 배치는 View에서 살펴볼 수 있게 됐습니다. 기능을 수정할 위치와 테스트할 범위가 더 분명해졌습니다. 앞으로 기능을 추가할 때도 실제 데이터를 누가 소유하는지, 변경을 어떤 경로로 전파하는지, 객체를 누가 유지하고 언제 연결을 해제하는지부터 결정하려고 합니다.
