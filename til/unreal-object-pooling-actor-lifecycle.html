반복 생성과 파괴의 비용

가장 단순한 총알 구현은 발사할 때 SpawnActor()로 생성하고, 적에게 맞거나 일정 시간이 지나면 Destroy()로 파괴하는 방식입니다. 발사 횟수가 적다면 충분히 사용할 수 있습니다.

하지만 여러 캐릭터가 동시에 연사하면 짧은 시간에 생성과 파괴가 반복됩니다. Actor 생성에는 메모리 할당 외에도 프로퍼티 초기화, 컴포넌트 생성·등록·초기화, Construction Script 실행, 게임 시작 상태에 따른 BeginPlay() 실행 등이 포함될 수 있습니다. 컴포넌트에 따라 렌더링·물리 상태를 준비하는 작업도 필요합니다.

Destroy()는 Actor를 종료하는 흐름으로 보내지만, 호출 즉시 객체 메모리를 회수한다는 뜻은 아닙니다. 게임플레이 종료 처리와 실제 가비지 컬렉션에 의한 메모리 회수는 구분해야 합니다. Epic Games의 Actor Lifecycle 문서에서 이 흐름을 확인할 수 있습니다.

만들어 둔 Actor 재사용하기

오브젝트 풀링은 만들어 둔 객체를 필요할 때 꺼내 쓰고, 사용이 끝나면 다시 사용할 수 있는 상태로 돌려놓는 방식입니다. 객체를 보관하고 관리하는 곳을 풀(Pool)이라고 합니다.

  • Prewarm: 처음 사용할 객체를 미리 생성합니다.
  • Acquire / Get: 대기 중인 객체를 대여합니다.
  • Release / Return / Recycle: 사용이 끝난 객체를 반환합니다.
  • Active / Inactive: 각각 사용 중인 상태와 다음 사용을 기다리는 상태입니다.

총알 10개를 준비하고, 추가 생성이나 파괴 없이 재사용한다면 다음과 같이 변합니다.

시점사용 중대기 중전체
준비 완료0개10개10개
1개 발사1개9개10개
추가로 2개 발사3개7개10개
1개 반환2개8개10개

반환은 반드시 특정 장소로 이동시킨다는 뜻이 아닙니다. 화면에서 숨기고 충돌과 이동 등을 멈춘 뒤 다시 대여할 수 있는 상태로 만드는 것이 중요합니다. 대기 중인 Actor도 World에 존재하고 메모리를 사용합니다.

여기서 재사용하는 것은 SpawnActor()로 생성한 Actor 인스턴스입니다. 같은 크기의 메모리 블록을 직접 할당·관리하는 메모리 풀과는 구분합니다. 같은 클래스의 Actor라고 관련 메모리 전체가 연속해서 배치되거나 메모리 사용량이 모두 같다는 뜻도 아닙니다.

Actor 수명과 사용 상태는 다르다

Bullet_0을 한 번 생성한 뒤 대여하고 반환하더라도 같은 인스턴스가 남습니다. 풀에서 꺼낼 때마다 BeginPlay()가 다시 호출되거나, 반환할 때 EndPlay()가 자동으로 호출되지는 않습니다.

Bullet_0 생성 → 대기 → 대여 → 사용 중 → 반환 → 대기 → 다시 대여
                         └──── 같은 Actor 인스턴스를 재사용 ────┘

Actor가 존재하는가와 지금 사용 중인가는 서로 다른 질문입니다. 일반적인 반환 과정에서는 재사용할 Actor에 Destroy()를 호출하지 않습니다. 실제로 파괴되는 Actor는 재사용 대상에서 제외해야 합니다.

따라서 매 대여·반환 시 수행할 작업을 별도 함수로 나눕니다. 아래 함수 이름은 구현 예시이며 Unreal의 기본 생명주기 함수가 아닙니다.

  • StartUse() — 사용 시작: 위치, 방향, 공격력, 이동 속도 등 이번 발사에 필요한 값을 설정하고 필요한 동작을 활성화합니다.
  • HandleReturned() — 사용 종료: 이동과 충돌을 멈추고, 사용 중 등록한 타이머와 효과, 이전 발사의 상태를 정리해 대기 상태로 돌립니다.

예를 들어 이전 발사의 만료 타이머가 남아 있으면, 다시 대여한 총알이 예상보다 일찍 반환될 수 있습니다. 화면에서 숨기는 것만으로 정리가 끝나지는 않으므로 Actor와 컴포넌트의 Tick, 이동, 충돌, 타이머 등 필요한 항목을 함께 관리해야 합니다.

같은 총알을 풀에서 10번 꺼내 쓴다고 BeginPlay()가 10번 실행되지는 않습니다. 매번 필요한 준비 작업은 별도의 사용 시작 함수가 담당해야 합니다.

풀링의 이점과 관리 비용

풀링은 반복적인 생성·파괴 횟수를 줄이고, 플레이 도중 발생할 생성 비용 일부를 사전 준비 시점으로 옮길 수 있습니다. 하지만 항상 더 빨라진다고 단정할 수는 없습니다.

  • 메모리: 대기 중인 객체도 메모리에 남으므로 풀 크기를 적절하게 정해야 합니다.
  • 준비 비용: 처음부터 너무 많이 생성하면 시작 시점에 부하가 몰립니다.
  • 상태 초기화: 이전 사용 상태가 다음 사용에 섞이지 않도록 초기화와 정리를 빠짐없이 처리해야 합니다.
  • 풀 고갈: 대기 객체가 없을 때 추가 생성할지, 요청을 거절할지 등의 정책이 필요합니다.
  • 대기 비용: 사용하지 않는 동안 불필요한 Tick이나 효과가 계속 실행되지 않도록 관리해야 합니다.

학습용 예제라면 풀 관리자의 BeginPlay()에서 소량을 미리 만들어 흐름을 관찰할 수 있습니다. 수천 개가 필요하다면 로딩 중에 준비하거나 여러 프레임에 나누어 생성하는 방법을 검토해야 합니다.

성능 개선 여부는 동일한 발사 조건에서 생성 시간, 프레임 시간, 메모리 사용량을 비교해 판단합니다. 이 글은 개념 정리이며, 실제 성능 개선 수치를 측정한 결과는 아닙니다.

배운 점

오브젝트 풀링은 생성 비용을 없애기보다 생성 횟수와 시점을 조절하고 이미 만든 객체를 재사용하는 설계입니다. 재사용 구조를 만들 때는 Actor의 생명주기와 풀의 대여·반환 흐름을 먼저 분리해야 합니다.

총알 풀을 구현할 때도 객체를 꺼내는 코드에 앞서, 사용 시작 시 덮어쓸 값과 반환 시 정리할 항목을 정리하겠습니다. 이 구분이 명확해야 같은 인스턴스를 다음 발사에서도 안전하게 사용할 수 있습니다.
