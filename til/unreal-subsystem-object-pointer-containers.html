Unreal Subsystem과 UObject 참조, 컨테이너 설계

기술 블로그 · 게임 엔진 · 2026.08.27

게임 시스템을 설계할 때는 “어디서든 접근할 수 있는가”보다 누가 소유하고 언제 사라지는지를 먼저 정해야 합니다. Unreal의 Subsystem으로 서비스의 수명을 정하고, TObjectPtr로 UObject 참조를 표현하며, 데이터의 관계에 맞춰 TArray, TSet, TMap을 선택하는 과정을 하나의 Quest 시스템으로 연결합니다.

Manager가 커질 때 생기는 문제

프로젝트가 커지면 QuestManager, SaveManager, AudioManager처럼 여러 기능을 조율하는 객체가 생깁니다. 이를 모두 UGameInstance의 멤버로 넣으면 접근은 쉽지만, 생성 순서·초기화·정리 책임과 의존성이 한 클래스에 쌓입니다. 결국 GameInstance가 서로 무관한 시스템을 모두 아는 거대한 서비스 저장소가 되기 쉽습니다. 

UCLASS()
class UMyGameInstance : public UGameInstance
{
    GENERATED_BODY()

    UPROPERTY()
    TObjectPtr<UQuestManager> QuestManager;

    UPROPERTY()
    TObjectPtr<USaveManager> SaveManager;
};

Subsystem은 이 문제를 “전역 Singleton 하나”가 아니라 특정 소유 객체의 수명에 귀속된 서비스로 풉니다. 엔진이 적절한 시점에 인스턴스를 만들고 Initialize와 Deinitialize를 호출하므로, 많은 경우 별도의 Singleton이나 수동 NewObject가 필요하지 않습니다.

Subsystem은 수명 단위의 서비스

타입인스턴스 범위적합한 예주의점
UEngineSubsystemEngine 인스턴스당 하나플랫폼 서비스, 전역 분석 기능개별 게임 세션이나 World 상태를 넣지 않음
UGameInstanceSubsystemGameInstance당 하나저장, 계정, 업적, 세션 퀘스트맵 전환 뒤에도 남아야 하는 상태인지 확인
UWorldSubsystemWorld마다 하나스폰, 월드 이벤트, 낮과 밤PIE와 서버 환경에는 World가 여러 개일 수 있음
ULocalPlayerSubsystemLocalPlayer마다 하나플레이어별 UI, 입력 설정로컬 멀티플레이에서는 여러 인스턴스가 존재
UEditorSubsystemEditor 수명 동안 하나에디터 도구와 자동화런타임 게임 시스템과 분리

Subsystem 선택 질문은 “전역에서 쓸까?”가 아니라 “이 상태는 Engine, GameInstance, World, LocalPlayer 중 누구와 함께 태어나고 사라져야 하는가?”입니다.

따라서 Subsystem은 전역 Singleton과 정확히 같지 않습니다. UWorldSubsystem은 World마다, ULocalPlayerSubsystem은 로컬 플레이어마다 생깁니다. PIE에서 여러 World를 실행하거나 로컬 플레이어가 둘이라면 같은 클래스의 Subsystem 인스턴스도 여러 개입니다.

Subsystem 구현과 의존성

UCLASS()
class MYGAME_API UQuestSubsystem : public UGameInstanceSubsystem
{
    GENERATED_BODY()

public:
    virtual void Initialize(FSubsystemCollectionBase& Collection) override;
    virtual void Deinitialize() override;

    void StartQuest(int32 QuestId);
};

void UQuestSubsystem::Initialize(FSubsystemCollectionBase& Collection)
{
    Super::Initialize(Collection);
    UE_LOG(LogTemp, Log, TEXT("Quest subsystem initialized"));
}

void UQuestSubsystem::Deinitialize()
{
    UE_LOG(LogTemp, Log, TEXT("Quest subsystem deinitialized"));
    Super::Deinitialize();
}

사용하는 쪽은 소유 객체를 통해 Subsystem을 조회합니다. 조회 결과가 없을 수 있는 문맥이라면 null 검사도 포함합니다.

if (UGameInstance* GameInstance = GetGameInstance())
{
    if (UQuestSubsystem* QuestSystem =
            GameInstance->GetSubsystem<UQuestSubsystem>())
    {
        QuestSystem->StartQuest(1001);
    }
}

다른 Subsystem이 먼저 준비되어야 한다면 초기화 순서를 우연에 맡기지 않습니다. Initialize에서 Collection.InitializeDependency<UOtherSubsystem>()를 사용하면 의존성을 명시할 수 있습니다. 반대로 단순한 편의 함수 묶음, 수명이 짧은 Actor 로직, 데이터 자체를 Subsystem으로 만들면 책임과 수명 경계가 다시 흐려집니다.

Tick은 정말 필요할 때만

World와 함께 살면서 프레임 업데이트가 필요한 시스템은 UTickableWorldSubsystem을 사용할 수 있습니다. 그러나 “Subsystem이니 계속 검사한다”는 설계는 프레임마다 불필요한 순회와 숨은 실행 비용을 만듭니다. 퀘스트 진행은 적 처치, 아이템 획득 같은 이벤트를 구독하고 상태가 바뀔 때만 갱신하는 편이 대개 명확합니다.

  • 연속적인 공간 계산이나 시간 기반 시뮬레이션처럼 매 프레임 값이 변하면 Tick을 검토합니다.
  • 게임플레이 사건에만 반응하면 델리게이트, 메시지 또는 명시적인 함수 호출을 우선합니다.
  • Tick을 쓴다면 활성 조건, 처리 빈도, 순회하는 데이터 양을 함께 측정합니다.

TObjectPtr와 GC의 관계

UPROPERTY()
TObjectPtr<UQuest> ActiveQuest;

TObjectPtr<T>는 std::shared_ptr처럼 참조 횟수로 객체를 소유하는 스마트 포인터가 아닙니다. GC가 관리하는 UObject를 가리키도록 만든 Unreal의 객체 포인터 래퍼이며, 에디터 빌드의 접근 추적과 향후 포인터 표현 변경을 위한 기반도 제공합니다. 일반 포인터처럼 ->와 bool 검사를 사용할 수 있고, raw pointer가 필요하면 Get()으로 꺼냅니다.

중요한 구분은 TObjectPtr라는 타입만 쓴다고 대상이 자동으로 살아남는 것은 아니라는 점입니다. UObject/USTRUCT의 장기 보관 멤버라면 보통 UPROPERTY로 리플렉션 시스템에 등록해야 GC가 강한 참조로 추적합니다. 커스텀 비리플렉션 참조를 보관해야 한다면 AddReferencedObjects 같은 별도 참조 보고 방식이 필요할 수 있습니다. 

// 장기 보관하는 멤버 참조
UPROPERTY()
TObjectPtr<AEnemy> TargetEnemy;

// 함수 안에서 잠깐 사용하는 참조
void Attack()
{
    AEnemy* Enemy = TargetEnemy.Get();
    if (IsValid(Enemy))
    {
        Enemy->TakeDamage(/* ... */);
    }
}

로컬 변수와 함수 인자처럼 GC 수집 구간을 넘어 보관하지 않는 참조는 raw pointer가 자연스럽습니다. 다만 raw pointer는 소유권이나 유효성을 보장하지 않으므로, 객체가 제거될 수 있는 경계를 넘는다면 참조 종류를 다시 선택해야 합니다.

강한·약한·소프트 참조 선택

타입대상을 살려 두는가주요 용도
TObjectPtr<T>UPROPERTY 등으로 추적되면 강한 참조소유 객체가 장기간 보관하는 UObject 멤버
TWeakObjectPtr<T>아니요대상이 사라져도 되는 런타임 관찰 참조
TSoftObjectPtr<T>로드 전에는 경로만 보관필요할 때 비동기 또는 지연 로드할 에셋
TStrongObjectPtr<T>예UPROPERTY를 둘 수 없는 범위에서 명시적으로 UObject 유지

캐릭터가 자신의 컴포넌트를 보관한다면 강한 프로퍼티 참조가 자연스럽습니다. 반면 현재 조준 중인 Enemy가 먼저 파괴될 수 있다면 TWeakObjectPtr가 의도를 더 잘 드러냅니다. 대형 무기 Mesh를 사용하기 전까지 로드하고 싶지 않다면 TSoftObjectPtr로 에셋 의존성과 메모리 상주 시점을 분리할 수 있습니다.

TArray·TSet·TMap 선택 기준

컨테이너핵심 관계게임 코드 예유의점
TArray<T>순서 있는 연속 배열인벤토리 슬롯, 웨이포인트중간 삽입·삭제 시 요소 이동 가능
TSet<T>유일한 값의 집합발견 지역, 해금 업적반복 순서를 의미 있는 순서로 가정하지 않음
TMap<K, V>유일한 Key와 Value의 대응Item ID → ItemDataFind 결과 포인터는 변경 후 무효화될 수 있음

TArray는 “몇 번째인가”가 의미 있을 때, TSet은 값의 유일성과 존재 여부가 핵심일 때, TMap은 Key로 데이터를 찾을 때 선택합니다. TSet과 TMap은 해시 기반이라 일반적인 탐색·추가·삭제가 평균적으로 상수 시간에 가깝지만, 해시 충돌과 재할당이 있으므로 무조건 O(1)이라고 단정하거나 반복 순서에 의존해서는 안 됩니다. 

TArray<FItem> Inventory;
TSet<FName> UnlockedAchievements;
TMap<int32, FItemData> ItemDatabase;

if (const FItemData* Item = ItemDatabase.Find(1001))
{
    UE_LOG(LogTemp, Log, TEXT("Found item: %s"), *Item->DisplayName.ToString());
}

TMap::Find는 Value의 포인터를 반환하므로 null 검사가 필요합니다. 이 포인터를 오래 저장한 채 Map에 요소를 추가하거나 제거하면 재할당으로 무효화될 수 있으므로, 조회한 범위 안에서 바로 사용하는 편이 안전합니다.

사용자 정의 Key의 조건

사용자 정의 타입을 TSet의 요소나 TMap의 Key로 쓰려면 동등성 비교와 해시 함수가 필요합니다. operator==가 두 값을 같다고 판단한다면 GetTypeHash도 반드시 같은 해시를 반환해야 합니다. 

USTRUCT()
struct FItemKey
{
    GENERATED_BODY()

    int32 ItemId = 0;
    int32 Level = 0;

    bool operator==(const FItemKey& Other) const
    {
        return ItemId == Other.ItemId && Level == Other.Level;
    }
};

uint32 GetTypeHash(const FItemKey& Key)
{
    return HashCombine(GetTypeHash(Key.ItemId), GetTypeHash(Key.Level));
}

비교에는 넣지 않은 필드를 해시에만 포함하거나, 실행 중 Key 값을 바꾸면 컨테이너가 올바른 버킷에서 항목을 찾지 못할 수 있습니다. Key는 컨테이너에 들어간 동안 사실상 불변 값으로 다루는 것이 좋습니다.

Quest 시스템으로 연결하기

UCLASS()
class MYGAME_API UQuestSubsystem : public UGameInstanceSubsystem
{
    GENERATED_BODY()

public:
    UQuest* FindQuest(int32 QuestId) const;
    bool IsCompleted(int32 QuestId) const;

private:
    UPROPERTY()
    TMap<int32, TObjectPtr<UQuest>> Quests;

    UPROPERTY()
    TSet<int32> CompletedQuestIds;
};

UQuest* UQuestSubsystem::FindQuest(int32 QuestId) const
{
    if (const TObjectPtr<UQuest>* Quest = Quests.Find(QuestId))
    {
        return Quest->Get();
    }

    return nullptr;
}

bool UQuestSubsystem::IsCompleted(int32 QuestId) const
{
    return CompletedQuestIds.Contains(QuestId);
}

이 선언에는 각 도구의 역할이 분명하게 드러납니다.

  • UGameInstanceSubsystem

    맵이 바뀌어도 이어지는 게임 세션 단위의 Quest 서비스 수명을 정의합니다.

  • TMap<int32, TObjectPtr<UQuest>>

    Quest ID로 객체를 찾는 관계와, Subsystem이 보관하는 강한 UObject 참조를 표현합니다.

  • TSet<int32>

    완료 ID가 중복되지 않으며 존재 여부 확인이 중요하다는 규칙을 표현합니다.

다만 퀘스트 정의가 변하지 않는 에셋 데이터라면 모든 정의를 런타임 UObject로 복제하기보다 UDataAsset이나 DataTable에 두고, Subsystem에는 진행 상태만 보관하는 설계도 검토할 수 있습니다. 또한 GameInstance 수명은 실행 중 맵 전환을 넘을 뿐, 프로그램을 종료한 뒤까지 데이터를 보존하지 않습니다. 영구 진행도는 SaveGame 등 별도의 저장 계층이 필요합니다.

정리

  • Subsystem은 접근 편의를 위한 전역 객체가 아니라 Engine, GameInstance, World, LocalPlayer 같은 소유자의 수명에 붙는 서비스입니다.
  • TObjectPtr는 참조 카운팅 스마트 포인터가 아니며, 멤버 강한 참조는 보통 UPROPERTY와 함께 선언해 GC가 추적하게 합니다.
  • 대상을 살려 둘 필요가 없으면 TWeakObjectPtr, 에셋을 나중에 로드하려면 TSoftObjectPtr를 검토합니다.
  • TArray는 순서, TSet은 유일성, TMap은 Key와 Value의 관계를 코드에 표현합니다.
  • 좋은 설계는 타입을 많이 쓰는 것이 아니라, 시스템 수명·참조 강도·데이터 관계를 실제 요구사항과 일치시키는 데서 시작합니다.
